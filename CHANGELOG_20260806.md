Updated **TranzorExporter.exe** (v20260806)

What's new in 6 August update — 502/503 storm resilience (Full Translations & MR/Scan channels):

**Root cause (2026-08-06 RCA).** The platform backend is a single uvicorn process behind a k8s ingress with a deliberately small DB pool (5+5); when the client's startup burst (summary + badge/src-count prefetch + light inventory, with 4–8-worker thread pools on the MR side) piles onto in-process ML inference, the ingress answers **502/503**. The Legacy channel (`export_translations._api_get`) already had the full defence stack — gate + 5xx retry + telemetry — but the **MR/Scan channel (`export_mr_pipeline`) had none**: HTTP 5xx was never retried (`raise_for_status` blew up the whole chain), requests were ungated, and a single 503 made `build_light_inventory` "succeed" with an empty list that the GUI cached green as **"0 products"** for the whole session — the panel looked dead until restart.

- 🛡️ **MR/Scan HTTP layer hardened** — `export_mr_pipeline._api_get` now mirrors the proven Legacy design: retries **429/500/502/503/504** at the single-request boundary with exponential backoff + jitter, honors numeric `Retry-After`, returns the final response after exhausted retries (caller `raise_for_status` semantics unchanged), and funnels every GET through a new process-level gate (`TRANZOR_MR_HTTP_WORKERS`, default 2 — same proven-stable value as the Legacy gate; combined worst-case in-flight is now ~4 instead of dozens). `ReadTimeout` still fails fast (pinned contract). `_api_post` gets the same gate plus a conservative **429/503-only** retry (POST is not idempotent — 500/502/504 may fire after the server already executed).
- 📡 **MR/Scan traffic now feeds the platform pill** — the same `conn_health.BUS` telemetry embeds as Legacy (in-flight registry, gate waits, retry events with `Retry-After`), so MR/Scan retries land in `~/.tranzor_exporter/conn_health.log` and wedge detection sees the whole picture, not just Legacy traffic.
- 🧬 **Full-text hydration off the raw session** — legacy-quality UNS hydration (6-wide fan-out used by Tranzor Checks / quality / post-edit paths) previously bypassed everything on a bare `requests.Session`; it now goes through the gated, retried `_api_get` facade.
- 🚨 **Inventory failure is now visible and self-healing** — `build_light_inventory` records per-source failures (`LightInventory.source_errors`). When **all** selected sources fail (the 502/503-storm shape), the Full Translations tab no longer shows a green "0 products": it shows the compacted error in red and **auto-retries after 15s → 30s → 60s** (skips silently while busy; never pops a login dialog on its own — an expired **or server-revoked** token stops the loop with a re-login hint, on both the pre-launch check and the mid-run 401 route). A previously loaded good inventory (and the user's product/language selection) **survives** a failed refresh — the total-failure check runs before any destructive tree/state mutation. Partial failures load what survived and name the failed source(s) in amber. Manual Refresh cancels/resets the auto-retry.
- ⏲️ **Retry-After capped at 30s** (both Legacy and MR/Scan `_retry_wait`) — a server/proxy answering `Retry-After: 600` must not pin a worker thread for 10 minutes.
- 🔎 **/dashboard/overview fan-out tamed** — the heaviest backend endpoint (~9 queries per call) was hit with up to 8 concurrent inventory hydration calls; the pool is now 4 and, with the gate, true concurrency is capped at 2.
- 🩹 **GBK console hardening** — `export_full_translations._log`'s bare `print` fallback (progress_cb=None, i.e. CLI runs) could raise `UnicodeEncodeError` on cp936/piped stdout for the ✓/⚠ inventory lines — escalating a 502/503 *soft* source failure into a hard crash. Now try/except-wrapped like every other retry logger in the repo.
- 🧪 **33 new tests** (`test_mr_api_resilience`, `test_light_inventory_errors`, `test_gui_inventory_retry`, plus a Retry-After-cap case in the existing Legacy suite) — 5xx retry/backoff/Retry-After semantics incl. the 30s cap, exhausted-retry passthrough, gate concurrency cap, telemetry event shapes (registry clean during backoff sleeps; broken/absent `conn_health` never breaks a request), POST retry policy, source-error bookkeeping, and Tk-free GUI surgery for the red/amber/auto-retry states incl. good-inventory preservation and the no-modal-on-auto-401 rule. Full suite verified under native GBK stdout. All existing contracts (`test_api_timeout`, telemetry shapes, auth fail-fast) stay green.

Server-side note: the platform never sends `Retry-After` and has no app-level rate limiter — the 502/503s are ingress-generated under upstream saturation. Client-side capping + backoff resolves the self-inflicted share; if residual 503s persist under external load, the fix is more replicas/workers or a larger DB pool on the platform side (out of scope for this repo).
